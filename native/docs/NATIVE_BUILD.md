# Нативные сборки: iPhone и Windows

Это техническая инструкция к исходному проекту 0.3.0+3 на Flutter 3.47.8. Подготовленные команды и workflow не являются подтверждением выполненной сборки или установки. Нативный интерфейс и PDF-просмотрщик запускаются в приложении, без WebView.

## Общая проверка

Flutter SDK должен иметь версию 3.47.8 (Dart 3.13.7). Команды выполняются из каталога `native/` общего репозитория либо из корня извлечённого Flutter-проекта:

```sh
flutter --version
flutter pub get --enforce-lockfile
flutter analyze --fatal-infos
flutter test
```

`pubspec.lock` хранится вместе с приложением. Если намеренно меняются зависимости, lock-файл обновляется и проверяется отдельно. Изменение платформенных настроек требует повторной сборки соответствующей платформы.

`pdfrx`/PDFium используют нативные build hooks. Для Linux-проверок нужны доступный в `PATH` Clang и системные средства C/C++-сборки. Первый запуск может загружать нативные зависимости. На Windows перед полным `flutter test` сначала соберите release: тест PDFium проверяет библиотеку именно из готовой поставки.

`test/native_pdf_engine_test.dart` явно задаёт `Pdfrx.pdfiumModulePath`: на Linux это `build/native_assets/linux/libpdfium.so`, на macOS — `build/native_assets/macos/libpdfium.dylib`, на Windows — `build/windows/x64/runner/Release/pdfium.dll`. Тестовый исполняемый файл Flutter находится в SDK, поэтому автоматический поиск библиотеки рядом с ним не подходит. Это настоящий нативный PDFium, а не замена движка. Тест открывает предоставленный 26-страничный PDF, отрисовывает страницу монтажа, проверяет отказ на повреждённом документе и переключение страниц в интерфейсе шириной 390 px. Снимки проверки записываются в `build/validation/` и `build/previews/`.

Калькулятор, встроенные инструкции и сохранённые PDF могут работать без сети. Локальный JSON не является синхронизацией между устройствами. Он содержит объекты, расчёты и диалоги, но **не PDF-файлы**. Для их переноса используйте «Сохранить PDF» и повторное добавление в нужные профили. Нативный экран помощника обращается к отдельному серверному API и требует интернета.

## Windows

Потребуется Windows с Flutter SDK и Visual Studio. В Visual Studio Installer установите workload **Desktop development with C++**; редактор Visual Studio Code его не заменяет.

```powershell
flutter config --enable-windows-desktop
flutter doctor -v
flutter devices
flutter pub get --enforce-lockfile
flutter run -d windows
```

После проверки приложения:

```powershell
flutter build windows --release
flutter test --no-pub test/native_pdf_engine_test.dart
```

Для стандартной x64-сборки результат находится в `build/windows/x64/runner/Release/`. Передавать нужно всю папку: исполняемый файл, библиотеки (включая `pdfium.dll`) и `data`, а не только `.exe`. Это portable-сборка приложения; установщик и подпись Windows в текущий workflow не входят. Пакет проверяется на отдельном Windows-компьютере, включая доступ к файлам и печать.

Официальная настройка: [Flutter — Windows development](https://docs.flutter.dev/platform-integration/windows/setup).

## iPhone: компиляция

Для iOS требуется macOS с Xcode и средствами сборки, совместимыми с выбранной версией Flutter. Для нативных зависимостей также могут потребоваться CocoaPods. Платформенный проект находится в `ios/`; минимальная версия системы для приложения и PDFium — iOS 15.

```sh
flutter doctor -v
flutter pub get --enforce-lockfile
flutter build ios --release --no-codesign
```

Эта команда проверяет компиляцию и создаёт неподписанный `build/ios/iphoneos/Runner.app`. Это **unsigned compile-only artifact**, не подписанная IPA и не готовый пакет для обычной установки на телефон.

Для запуска на подключённом личном устройстве в Xcode нужны выбранная команда разработчика, принадлежащий владельцу Bundle ID, доверие устройству и Developer Mode. Бесплатный Apple Personal Team допускает личное тестирование, но provisioning-профили истекают через 7 дней, после чего приложение требуется собрать и установить заново. Такой вариант не равен постоянному распространению приложения.

Официальные сведения: [Flutter — iOS setup](https://docs.flutter.dev/platform-integration/ios/setup), [Apple — Personal Team и программы разработчика](https://developer.apple.com/help/account/basics/about-your-developer-account).

## Подписанная IPA и TestFlight

Для выпуска через TestFlight/App Store потребуются Apple Developer Program и настройка приложения в App Store Connect. После подготовки команды, идентификатора и подписи используется:

```sh
flutter build ipa --release
```

На этом этапе нужно проверить итоговый архив, подпись, разрешения и сборку на настоящем iPhone. Загрузка в TestFlight выполняется отдельно. Текущий workflow не создаёт сертификаты, provisioning-профили и подписанные IPA, не принимает соглашения и ничего не публикует.

Учётные данные Apple, сертификаты и ключи не добавляются в Git и не передаются в чат. Когда подписанная сборка будет подготовлена, они настраиваются в защищённом хранилище сборочной среды владельца.

Официальная инструкция: [Flutter — build and release an iOS app](https://docs.flutter.dev/deployment/ios).

## Ручная сборка в GitHub Actions

Файл: `.github/workflows/native-builds.yml`. Он должен находиться в корне репозитория именно этого Flutter-приложения.

1. Откройте **Actions → Native builds → Run workflow**.
2. Выберите ветку и нужные платформы: Windows и/или unsigned iOS.
3. Сначала должны успешно завершиться анализ и тесты на Ubuntu.
4. Для Windows скачайте артефакт `windows-x64-portable-…`, распакуйте целиком и проверьте запуск.
5. Артефакт `ios-unsigned-COMPILE-ONLY-…` содержит скомпилированную неподписанную `.app`; для установки потребуется отдельная подпись.

Ручной workflow извлечённого Flutter-проекта работает по `workflow_dispatch`. В общем репозитории используется корневой `.github/workflows/native-app-preview.yml`: он запускается при изменениях `native/**`, собирает текущий commit, проверяет PDFium из Windows release-папки, добавляет в пакет подписанные Microsoft CRT и проверяет запуск процесса; iPhone компилируется на `macos-15-intel` без подписи. Публикации в магазинах нет. Использование GitHub-hosted runners зависит от настроек и доступных минут аккаунта владельца. Результаты каждой новой сборки проверяются по журналу конкретного запуска; наличие workflow само по себе не подтверждает успешную сборку.

GitHub Actions зафиксированы проверенными SHA: checkout v6, upload-artifact v6 и flutter-action v2. Flutter SDK зафиксирован на 3.47.8. Результаты native-сборок необходимо проверять по фактическим журналам конкретного запуска.

## Серверный помощник

Текущие `/api/auth` и `/api/chat` веб-проекта используют подписанную cookie-сессию и проверку Origin. Начиная с версии 0.2.0 приложение использует отдельные `/api/native/auth` и `/api/native/chat`; они опубликованы на `https://my-gpt-chat-theta.vercel.app` и совместимы с клиентом 0.3.0. Браузерная проверка Origin сохранена, ключ OpenAI остаётся на сервере. Нативный bearer имеет отдельное назначение и подпись, не заменяет cookie сайта и хранится только в оперативной памяти клиента. Проверки доступности и отказа без авторизации не подтверждают реальный ответ ИИ: запрос с паролем владельца проверяется отдельно. Облачная синхронизация пока не подключена.

## Библиотека PDF

Добавление выполняется явно для выбранного профиля: системный выбор PDF либо загрузка по PDF-ссылке каталога. Ссылки могут вести на сайт производителя или зеркало; приложение хранит исходный URL, время добавления, имя, размер и происхождение. Наличие источника в каталоге не подтверждает актуальность полного документа. Профили без источника помечены как памятки; предоставленный оригинальный PDF «Металл Профиль» (3-е издание, 2019, 26 страниц) остаётся в комплекте без изменений.

`ManualLibrary` допускает PDF до 30 МиБ и до 500 привязок. Сетевой загрузчик использует HTTPS без cookies и авторизации, до трёх HTTPS-перенаправлений, лимит переданных распакованных данных и общий таймаут 45 секунд. Сигнатура PDF проверяется при сохранении; полноценный разбор выполняет PDFium при открытии. PDF-ссылки внутри просмотрщика отключены.

Файлы лежат в `manual-library/pdfs/<sha256>.pdf` в application-support каталоге; отдельный `manifest.json` связывает их с ID профилей. Перед чтением проверяются размер и SHA-256. При повреждении списка новые записи блокируются, исходные файлы сохраняются; автоматического восстановления через интерфейс пока нет. Удаление привязки сохраняет файл в хранилище, чтобы не затронуть другие профили. PDF не отправляются на сервер и не входят в JSON-копию workspace.

## Границы проверки

Анализ Dart и Flutter widget tests могут выполняться на Linux. Они не проверяют Xcode, подпись Apple, Windows SDK, установку на устройство, системный диалог файлов или печать на целевых ОС. Эти проверки завершаются на соответствующих платформах до выдачи установочных пакетов пользователю.
